## Таблица 4.8 – Влияние дообучения на точность прогноза во времени

**Цель:** показать, что периодическое дообучение модели на скользящем окне
компенсирует дрейф статистики нагрузки.

**Датасет:** Azure VM Trace 2019 (30 суток — достаточно длинный для 8-суточного
тестового периода, в отличие от Alibaba).

**Конфигурация:**
- Начальное обучение на первых ~22 сутках
- 4 тестовых сегмента по 2 суток: «Сутки 1-2», «Сутки 3-4», «Сутки 5-6», «Сутки 7-8»
- Конфигурации: **с дообучением** (перед каждым сегментом — retrain на скользящем
  окне 2016 наблюдений = 7 суток) и **без дообучения** (одна модель на все сегменты)
- Seeds: 42, 137 (2 seeds — тест медленный из-за многократного обучения)

**Запуск:**
```powershell
python -u scripts/run_table.py 4.8
```

**Ожидаемое время:** ~30–40 минут (GPU).
На каждый seed в режиме «с дообучением» выполняется 1 начальный fit + 3 retrain
+ 4 прогноза по 576 точек. В режиме «без дообучения» — 1 fit + 4 прогноза.

**Формат [METRIC] строк:**
```
[METRIC] TABLE_4_8: period=Сутки_1-2 | MAE_with_retrain=0.0260±0.0010 | MAE_no_retrain=0.0262±0.0012 | diff_pct=+0.77%
```

## Таблица 4.9 – Влияние календарных признаков

**Цель:** количественно оценить вклад 6 тригонометрических временных признаков
(синусы/косинусы часа суток, дня недели, минуты часа) во входной вектор GRU.

**Датасет:** синтетический **«Стационарный»** (4320 точек, 15 суток, чёткая
суточная сезонность с периодом 288 и умеренный шум).

Почему синтетический, а не реальный:
- На Google CPU стабильная и низкая (0.15–0.25) → GRU сводится к
  persistence, календарные признаки игнорируются.
- На Alibaba (2243 точки ≈ 7.8 суток) недельный цикл не успевает проявиться,
  автокорреляция ряда затеняет вклад временных признаков.
- Синтетический «Стационарный» по дизайну содержит суточную сезонность
  как основной сигнал — вклад календарных признаков там измеряется
  наиболее чисто.

**Конфигурация:**
- **С календарными**: d_step = 8 (cpu_norm + stl_resid + 6 временных)
- **Без календарных**: d_step = 2 (cpu_norm + stl_resid)
- Сеть `GRUQuantileNet` пересоздаётся с нужным d_step. Все остальные
  гиперпараметры из `config.yaml` остаются без изменений.
- Seeds: 42, 137, 256

**Реализация:** подкласс `HybridForecasterNoCalendar` в `tests/test_table_4_9.py`
переопределяет:
- архитектуру сети (`GRUQuantileNet` с `d_step=2`)
- `_stack_features()` для прогноза (возвращает 2 канала вместо 8)
- `fit()` — использует кастомный `TimeSeriesDatasetNoCalendar`, который
  возвращает только [cpu_norm, stl_residual] без 6 временных признаков

Это важно: стандартный `TimeSeriesDataset` всегда создаёт 7 или 8 признаков,
поэтому без переопределения обучения d_step не совпал бы между fit и predict.
Основной код `predictor/forecaster.py` не меняется.

**Запуск:**
```powershell
python -u scripts/run_table.py 4.9
```

**Ожидаемое время:** ~10–15 минут (GPU).

**Формат [METRIC] строк:**
```
[METRIC] TABLE_4_9: dataset=Stationary | config=with_calendar | MAE=0.0310±0.0001 | seeds_ok=3/3
[METRIC] TABLE_4_9: dataset=Stationary | config=no_calendar   | MAE=0.0360±0.0008 | seeds_ok=3/3
[METRIC] TABLE_4_9: improvement_pct=+16.13%
```
(Значения примерные; на синтетическом ряду с суточной сезонностью
ожидается наиболее выраженная разница с/без календарных признаков.)

В per-seed логах дополнительно выводятся `d_step` (8 vs 2 — проверка,
что нужная архитектура действительно активна) и `blend_alpha` — чтобы
видеть, насколько GRU реально используется vs persistence.

Строка `improvement_pct` показывает, на сколько процентов ухудшается MAE
при отключении календарных признаков (положительное значение = календарные
признаки помогают).

## Таблица 4.10 – Анализ абляции компонентов метода

**Цель:** оценить вклад каждой компоненты метода (STL, квантильная оценка,
гистерезис, адаптивный порог) через изолированное отключение.

**Датасет:** Alibaba Cluster Trace 2018, горизонт h = 3.

Выбран Alibaba (а не Google), потому что его утилизация CPU находится
в рабочем диапазоне 0.4–0.9. На Google CPU слишком низкая (0.15–0.25),
из-за чего формула `r_req = ceil(q_upper / cpu_target)` всегда даёт
r_req ≤ 2 и ограничение r_min = 2 делает масштабирование невозможным —
эффект разных конфигураций становится невидим.

**Важный технический момент:** прогноз forecaster'а даётся в долях
cpu ∈ [0,1], но decision module ожидает «предсказанную суммарную
нагрузку в единицах реплик». Поэтому в симуляции прогноз масштабируется
на текущее число реплик: `load_scaled = q_upper * r_cur`.

**Конфигурации (5 штук):**

1. **Полный метод** — HybridForecaster + стандартный ResourceDecisionModule.
2. **Без STL-декомпозиции** — `AutoGRUForecaster` (тот же GRU, но без
   предобработки) + стандартный DM.
3. **Без квантильной оценки** — HybridForecaster, но в симуляции решений
   вместо реальных квантилей GRU используется точечный прогноз с
   фиксированным буфером 20%: `q_up = median*1.2`, `q_lo = median*0.8`.
4. **Без механизма гистерезиса** — HybridForecaster + DM с `tau=1`
   (масштабирование вниз без накопления подтверждений).
5. **С фиксированным δ=1** — HybridForecaster + `FixedDeltaDecisionModule`
   (подкласс, в котором `delta_t` жёстко задан равным 1.0 вместо
   адаптивного `β · ci_width / cpu_target`).

**Для каждой конфигурации** симулируется цикл управления:
на каждом шаге — predict, вызов `DecisionModule.step(q_up, q_lo)`,
запись истории `r_fin`. Затем вычисляются:
- **MAE** (через `compute_mae`)
- **Нарушения SLA, %** (через `compute_sla_violations`) — доля шагов, где
  `cpu_actual > cpu_target * r_fin`
- **Средняя утилизация, %** (через `compute_avg_utilization`)
- **Число операций масштабирования** (через `compute_scale_ops`)

**Seeds:** 42, 137, 256 (3 прогона).

**Запуск:**
```powershell
python -u scripts/run_table.py 4.10
```

**Ожидаемое время:** ~30–40 минут (GPU).

**Формат [METRIC] строк:**
```
[METRIC] TABLE_4_10: dataset=Alibaba | config=full          | label="Полный метод"             | MAE=0.0452±... | SLA=...% | UTIL=...% | OPS=...
[METRIC] TABLE_4_10: dataset=Alibaba | config=no_stl        | label="Без STL-декомпозиции"     | MAE=0.0480±... | SLA=...% | UTIL=...% | OPS=...
[METRIC] TABLE_4_10: dataset=Alibaba | config=no_quantile   | label="Без квантильной оценки"   | MAE=0.0452±... | SLA=...% | UTIL=...% | OPS=...
[METRIC] TABLE_4_10: dataset=Alibaba | config=no_hysteresis | label="Без механизма гистерезиса"| MAE=0.0452±... | SLA=...% | UTIL=...% | OPS=...
[METRIC] TABLE_4_10: dataset=Alibaba | config=fixed_delta   | label="С фиксированным δ=1"      | MAE=0.0452±... | SLA=...% | UTIL=...% | OPS=...
```

**ВАЖНО о MAE:** у конфигураций `no_quantile`, `no_hysteresis`, `fixed_delta`
MAE идентичен `full` — это **ожидаемое поведение**, а не ошибка. Они изменяют
только модуль принятия решений, не сам прогноз. Смысл абляции именно в том,
чтобы показать: при одинаковой точности прогноза разные стратегии управления
дают разное SLA/UTIL/OPS. Различия ищите в колонках SLA, UTIL, OPS.

Ожидаемое поведение (для диссертации):
- `no_stl`: MAE хуже — подтверждает вклад декомпозиции
- `no_quantile`: MAE тот же (медиана не меняется), но SLA violations растут
- `no_hysteresis`: SLA практически не меняется, но OPS (операции масштабирования) резко растут
- `fixed_delta`: SLA растут, UTIL падает — адаптивный порог лучше

## Таблица 4.11 – Вычислительное время по модулям

**Цель:** оценить вклад каждого шага итерации управления в общее время.

**Датасет:** Alibaba Cluster Trace 2018.

**Конфигурация:**
- Seed = 42 (один прогон — тест только для timing)
- N_ITERS = 50 итераций
- Warmup: 3 холостых predict перед замерами (JIT компиляция CUDA)
- Δt = 5 мин = 300 000 мс (для расчёта процента от интервала)

**Модули замера:**
1. **PromQL-запрос** — моделируется попыткой HTTP-запроса к `127.0.0.1`
   (реальный запрос к Prometheus в кластере имеет похожий порядок задержки 5–15 мс).
2. **Предобработка (IQR + STL)** — полный вызов `Preprocessor.transform()`
   на скользящем окне 3 периодов (~864 наблюдения).
3. **Прогноз тренда и сезонности** — в актуальной архитектуре не используется
   как отдельный шаг (GRU предсказывает нормализованный CPU напрямую),
   строка оставлена для совместимости с таблицей главы 4 со значением 0.
4. **Вывод GRU-модели** — forward pass по сети `GRUQuantileNet`.
5. **Принятие решений** — `ResourceDecisionModule.step(q_up, q_lo)`.
6. **PATCH к Kubernetes API** — не замеряется (требует реального кластера).
   Берётся типичное значение 25±10 мс из документации.
7. **Полный цикл** — измеряется end-to-end от начала до конца итерации.

**Запуск:**
```powershell
python -u scripts/run_table.py 4.11
```

**Ожидаемое время:** ~2–3 минуты.

**Формат [METRIC] строк:**
```

[METRIC] TABLE_4_11: module=preprocess   | mean_ms=4.20 | std_ms=0.40 | pct_of_dt=0.0014%
[METRIC] TABLE_4_11: module=trend_season | mean_ms=0.00 | std_ms=0.00 | pct_of_dt=0.0000%
[METRIC] TABLE_4_11: module=gru_forward  | mean_ms=0.80 | std_ms=0.10 | pct_of_dt=0.0003%
```
